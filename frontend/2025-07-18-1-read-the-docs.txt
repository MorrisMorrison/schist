● Based on my research, here are three implementation approaches for nested docs, each with different
  trade-offs:

  Proposal 1: Filesystem Folders (Recommended)

  1:1 mapping between filesystem structure and doc organization

  Implementation:
  - Store docs in nested directories: /data/folder1/subfolder/page.md
  - Use file path as document identifier instead of flat slug
  - Add path field to metadata for breadcrumb navigation
  - API routes become path-based: /api/docs/folder1/subfolder/page

  Pros: Natural, intuitive, easy file management, scales well
  Cons: Requires path-based routing changes, file moving complexity

  Proposal 2: Metadata Hierarchy

  Virtual folders using parent/child relationships in frontmatter

  Implementation:
  - Keep flat file storage, add parent_slug and folder_type to metadata
  - Build tree structure in memory from parent relationships
  - Virtual folder "pages" with special metadata flags
  - Current slug-based API remains mostly unchanged

  Pros: Minimal storage changes, flexible organization, easy API migration
  Cons: Less intuitive, potential inconsistency, complex tree building

  Proposal 3: Hybrid Approach

  Filesystem structure + metadata tracking

  Implementation:
  - Use directories for organization but also track in metadata
  - Add folder_path, parent_folder, depth to frontmatter
  - Filesystem provides structure, metadata enables rich features
  - Support both path-based and slug-based access

  Pros: Best of both worlds, robust, feature-rich
  Cons: More complex, potential sync issues between filesystem and metadata

  My Recommendation: Proposal 1 (Filesystem Folders)

  This is the most natural approach that aligns with user expectations and provides the foundation for
  advanced features like file tree navigation and breadcrumbs.
